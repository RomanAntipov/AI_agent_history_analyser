# Навык анализа истории объектов и классов (Advanced)

Этот навыint навык позволяет агенту выполнять два типа задач: поиск истории конкретного объекта по его ID и поиск объектов в классе по заданным критериям (включа/не включая анализ изменений внутри JSON-структуры).

## 1. Предварительные требования

- **Доступ к БД**: PostgreSQL через `psql`.
- **Конфигурация**: Учетные данные для подключения необходимо брать из файла `.env` в корне проекта.
- **КРИТИЧЕСКИЙ ШАГ**: Перед выполнением любой операции агент **ОБЯЗАН** проверить подключение к базе данных (например, `psql -c "SELECT 1"`). Если база данных недоступна, агент должен **ОСТАНОВИТЬСЯ** и немедленно уведомить пользователя.

## 2. Терминология и Схема таблицы

### Терминология
- **`table_name` / `class_name`**: Имя класса или таблицы (например, `nsi_Bank`).
- **`table_id`**: Системный UUID таблицы, полученный из `system.schemas`.
- **`history_table_name`**: Имя таблицы в схеме `history`, сформированное на основе `table_id` (например, `obj_0ec65337_6ede_4c6f_a8ed_81bb6dc4e3f2_history`).
- **`object_id`**: UUID конкретного объекта, историю которого мы ищем.
- **`object_json`**: Поле `object` в таблице истории, содержащее сериализованный JSON с данными объекта.

### Схема таблицы истории (схема `history`)
Все таблицы истории имеют следующую структуру:
- `object_id` (varchar): Уникальный идентификатор объекта.
- `object_revision` (bigint): Номер ревизии.
- `object` (jsonb/text): Сериализованные данные объекта.
- `object_name` (text): Имя объекта на момент данной ревизии.
- `state` (varchar): Состояние объекта (например, 'ACTIVE', 'DELETED').
- `date` (timestamp): Временная метка создания данной ревизии.
- `author` (varchar): Пользователь, выполнивший действие.
- `object_create_date` (timestamp): Исходная дата создания объекта.
- `object_creator` (varchar): Пользователь, который исходно создал объект.

## 3. Протокол обнаружения таблицы (Discovery Protocol)

Агент **НЕ ДОЛЖЕН** пытаться искать таблицу истории напрямую по имени класса в `information_schema`. Он **ОБЯЗАН** следовать строгому алгоритму:

1.  **Проверка подключения**: Выполнить `psql -c "SELECT 1"`. Если ошибка — стоп.

2.  **Определение `table_id`**:
    - **Если ввод — это UUID (ID таблицы)**: Использовать его как основу.
    - **Если ввод — это имя (класса или таблицы)**:
        1. Найти `table_id` через запрос к `system.schemas`:
           `SELECT id FROM system.schemas WHERE name = '<table_name>' OR system_name = '<table_name>'`
        2. Если не найдено, выполнить поиск по шаблону:
           `SELECT id FROM system.schemas WHERE name LIKE '%<pattern>%' OR system_name LIKE '%<pattern>%'`
        3. Если после поиска `table_id` не обнаружен: сообщить об ошибке и остановиться.

3.  **Формирование имени таблицы истории**:
    - **КРИТИЧЕСКИЙ ШАГ**: При формировании `history_table_name` вы **ОБЯЗАНЫ** заменить все дефисы (`-`) на подчеркивания (`_`) в `table_id`. Игнорирование этого правила приведет к ошибке синтаксиса SQL (`syntax error at or near '-'`).
    - Взять полученный `table_id`.
    - Заменить все дешфы (`-`) на подчеркивания (`_`).
    - Итоговый формат: `history.obj_<transformed_id>_history`.
    - *Пример*: `47ce6f50-aa38-4514-ba03-17e146ec2bf6` -> `history.obj_47ce6f50_aa38_4514_ba03_17e146ec2bf6_history`.

4.  **Проверка существования таблицы**:
    - Выполнить: `psql -c "SELECT 1 FROM history.<history_table_name> LIMIT 1;"`
    - Если таблицы не существует или нет прав — сообщить об ошибке и остановиться.

## 4. Режимы работы

### Режим 1: Point Lookup (Поиск конкретного объекта)
*Используется, когда предоставлен `object_id`.*

- **Задача**: Получить все ревизии конкретного объекта.
- **Алгоритм**:
    1. Проверить количество ревизий:
       `SELECT count(*) FROM history.<history_table_name> WHERE object_id = '<object_id>'`
    2. **Обработка большого количества ревизий**:
       - **Если количество ревизий > 100**:
         - Сообщить пользователю: "Найдено [N] ревизий для объекта. Это слишком много для одного вывода."
         - Спросить пользователя, нужно ли увеличить `LIMIT` или ограничить поиск по дате (`since_date`).
    3. Выполнить основной запрос:
       ```sql
       SELECT * FROM history.<history_table_name>
       WHERE object_id = '<object_id>'
       [AND date >= '<since_date>'] -- если указана дата
       ORDER BY object_revision DESC
       LIMIT <depth>; -- по умолчанию 10, если не указано иное
       ```
    4. **Сортировка**: Всегда `ORDER BY object_revision DESC`.

### Режим 2: Criteria Search (Поиск по критериям в классе)
*Используется, когда нужно найти объекты по свойствам или изменениям.*

- **Задача**: Найти объекты, соответствующие условию.
- **Алгоритм**:
    1. Определить путь к полю в JSON (например, `object->>'name'`).
    2. Если требуется поиск **изменений**, использовать оконную функцию `LAG()`.
    3. Пример запроса (Поиск изменений поля `nameInPayment`):
       ```sql
       SELECT object_id, object_revision,
              object::jsonb->>'nameInpayment' as current_name,
              prev_name
       FROM (
           SELECT object_id, object_reg_revision, object,
                  LAG(object::jsonb->>'nameInpayment') OVER (PARTITION BY object_id ORDER BY object_revision) as prev_name
           FROM history.<history_table_name>
       ) sub
       WHERE current_name IS DISTINCT FROM prev_name;
       ```
## 5. Технический справочник SQL (Toolkit)

При работе с колонкой `object` (JSONB/TEXT) используй:

- **Приведение типов**: Всегда используй `object::jsonb` при обращении к полям, чтобы избежать ошибок, если тип колонки `text` или `varchar`.
  *Пример*: `object::json->>'KeyName'`
- **Чувствительность к регистру**: Помни, что ключи в JSON **чувствительны к регистру** (например, `CorAccount` и `cor_account` — это разные ключи). Перед написанием запроса проверь точный регистр ключей, изучив пример JSON.
- **Извлечение текста**: `object::jsonb->>'field_name'`
- **Извлечение по пути**: `object::jsonb#>>'{path,to,field}'`
- **Фильтрация**: `WHERE object::jsonb->>'City' LIKE '%Калининград%'`
- **Сравнение ревизий**: `LAG(column) OVER (PARTITION BY object_id ORDER BY object_revision)`

## 6. Обработка ошибок и вывод

- **Таблица не найдена**: Сообщить, что `table_id` не найден в `system.schemas`.
- **Пустой результат**: Если для `object_id` нет ревизий, вернуть пустой массив `[]`.
- **Формат вывода**: Результат должен быть сохранен в файл `history_<object_id_or_table_name>.json` в корне проекта.
- **Структура JSON**: Чистый массив объектов, легко парсимый.
